# 安全生产管理 Web/后端主线 + 微信小程序并行线：AI 编程分段任务包 v2

> 适用项目：物化院有限公司安全教育平台
> 默认项目目录：`E:\codex\safety`
> 基于文件：上一版《安全生产管理 Web 端与微信小程序：AI 编程分段任务包》
> 本次调整：保留 P01、D00—D40、R01—R03 的业务范围与原任务编号，改变依赖、执行泳道和交接方式。
> 已知状态：用户已确认微信小程序已经申请；这只解除“尚未申请账号”的阻塞，不等于合法域名、隐私、类目、体验版或正式审核已经全部通过。

## 一、本版采用的开发方式

不采用“Web 全部完成后才开始小程序”，也不采用“两端从第一天各写一套业务逻辑”。

采用以下方式：

1. **Web/后端主线拥有唯一业务规则**：数据库迁移、RLS、认证、项目/人员/培训/考试/签字/资格状态机、提醒事件、离线同步协议和 Web/H5。
2. **微信小程序并行线提前启动**：先做环境、工程骨架、API SDK、微信登录 POC 和平台能力验证；只在对应后端接口达到冻结门后接入真实业务。
3. **客户端不复制规则**：小程序不得自行判断“是否可上岗”、考试是否通过、是否需要复训或用户可看哪些项目，只展示服务端结果。
4. **跨线任务拆成配对子步骤**：D28、D30、D34 分为 `-BE` 与 `-MP`，分别交给 Web/后端 AI 和小程序 AI；原 D 编号仍是统一验收里程碑。
5. **Web/H5 发布候选版不再是小程序开工前置**：D28、D29 可很早开始；D32—D35 按 G1/G2/G3 契约门逐步解锁。
6. **联合测试仍是硬门**：D27 与 D36 都通过后，才能执行 D37、D38 和真实项目试点。

## 快速开发执行补充规则

> 本节优先解释本任务包中所有 D 内部执行节奏。目标是缩短开发周期，而不是降低安全或验收标准。D00—D40 继续作为业务里程碑台账，不把编号数量直接等同于开发工作量或项目完成百分比。

1. **一个 D 作为一个连续开发包推进。** D 编号是正式业务里程碑；Dxx-1、Dxx-A/B/C 等仅是内部执行切片，不是独立里程碑。没有 P0/P1、真实阻塞或必须人工介入时，AI 应连续完成后续内部步骤，不因每个小步骤结束而等待总控确认，也不得提前开始下一个 D。
2. **内部步骤不重复套正式流程。** 内部步骤默认不单独 CANDIDATE/PASS、不单独 R01/R03、不单独 commit/push、不单独生成完整 handoff。必要的状态只作为进度记录。
3. **完整 D 的默认快速主流程固定为：** `连续开发内部步骤 → FAST / 必要 TARGETED → D 全部功能完成 → 一次 FINAL → CANDIDATE → 一次 R01 → 仅在 R01 有 P0/P1/阻塞时执行正式 R02 → 必要 TARGETED/FINAL → R03（交接 + 显式 commit）→ PASS → 安全 fast-forward push`。除阶段门外，不得再嵌套第二套正式审查流程。
4. 测试分为 FAST / TARGETED / FINAL / GATE：
   - **FAST**：每次修改只跑直接受影响的短测试。
   - **TARGETED**：内部步骤或缺陷修复完成后，只跑受影响的数据库、RLS、API、页面或模块测试；不要求每个内部步骤重复运行同一套 TARGETED。
   - **FINAL**：当前 D 的全部开发完成后原则上只运行一次 D 级完整验收。
   - **GATE**：仅阶段冻结门、发布门和联合测试运行跨系统全量测试。
5. 原文所有类似“完成后运行 lint、类型、单元、集成、端到端、构建、迁移和安全测试”的表述统一解释为：完整测试在当前 D 的 FINAL/GATE 阶段运行；内部步骤只执行必要 FAST/TARGETED。
6. **focused review 不是内部步骤默认门禁。** 只有总控/用户明确要求，或已有具体失败/证据表明可能存在 P0/P1 且现有 TARGETED 不能充分判断时才进行；不得仅因 RLS、权限、Storage、历史不可变等领域“高风险”就自动追加复核。内部开发阶段发现 P0/P1 时执行“最小复现 → focused 修复 → 对应 TARGETED”，不记作正式 R02。修复通过且没有新的具体 P0/P1 证据后立即继续下一内部步骤，禁止形成多轮“复核—修复—再复核”循环。
7. 同一失败最多直接重跑一次。第二次出现同类失败必须改为最小复现和定向修复。
8. FINAL 失败后禁止立即整套重跑：提取失败步骤、定向修复、TARGETED 通过、所有阻塞项关闭，最后只再运行必要 FINAL。
9. R01/R02/R03 只对完整 D 执行：
   - D 全部开发完成并达到 CANDIDATE 后才运行一次 R01；
   - 正式 R02 只在 R01 发现 P0/P1/阻塞问题时运行；
   - R02 只修 P0/P1/阻塞，先运行问题相关最小复现和 TARGETED；
   - 阻塞关闭后只运行必要 FINAL；
   - R01 PASS 后运行一次 R03；
   - D 内部切片不得单独要求正式 R01-R03。
10. 问题分流：当前修改引入、当前验收明确要求、P0/P1、真实阻塞项必须当前处理；P2/P3 或不影响当前 D 的旧问题登记到追踪矩阵/交接后默认后移，不得因为追求完美反复暂停主线。已登记 P2/P3 只有出现新证据升级为 P0/P1 时才重新阻塞。
11. 每个完整 D 必须单独提交、验收、交接，但内部步骤默认不 commit、不 push；仅当存在需要独立隔离的安全/生产修复时，由总控明确批准例外提交。默认正式分支为：Web/后端 `track/web-backend`，小程序 `track/miniprogram`，集成 `integration/dual-track`。
12. 新 D 第一轮优先读取当前交接、当前任务、git 状态、当前 diff、受影响模块、必要契约和最近测试，不得无条件重新盘点整个仓库；同一 D 后续轮次只读取当前 diff、失败日志和直接相关代码，信息不足时再扩大范围。
13. 快速开发优先完成试点核心链路，不为追求完美提前进行无关重构、重复文档、性能优化或非阻塞增强功能。
14. 快速开发不降低以下硬红线：RLS、权限隔离、敏感信息/隐私、历史数据不可变、迁移安全、服务端权威业务规则、审计、数据完整性、上岗资格正确性和阶段发布门。任何为了提速而关闭 RLS、放宽权限、跳过关键负向测试、硬编码结果或吞异常的做法都禁止。
15. 建议每个新 D 使用新的 Codex 对话；Web/后端对话继续绑定 `E:\codex\safety-web` 和 `track/web-backend`，不因换对话重新从 D00 开始。

## 二、建议的两个 AI 工作区

建议使用两个独立 Git worktree；仓库存在未提交改动时不得强行创建、重置或清理，先由 D02 生成安全操作方案。

| 工作区 | 建议目录 | 建议长期集成分支 | 主要所有权 |
|---|---|---|---|
| Web/后端主线 | `E:\codex\safety-web` | `track/web-backend` | 数据库、迁移、RLS、后端、共享契约、Web/H5、定时任务 |
| 微信小程序并行线 | `E:\codex\safety-mini` | `track/miniprogram` | `miniprogram/**`、微信客户端适配、客户端状态、组件和小程序测试 |
| 集成与发布 | 原仓库或独立工作树 | `integration/dual-track` | 按契约版本合并、联合测试、发布候选版 |

### 文件所有权规则

- Web/后端线默认不得修改 `miniprogram/**`。
- 小程序线默认不得修改数据库迁移、RLS、服务端资格逻辑、Web/H5 页面和共享业务实现。
- 共享契约、原因码、事件 schema 和生成类型由 Web/后端线发布；小程序线消费。
- 小程序发现缺少接口时，使用本文件的 `C01` 变更单对话，不得在自己的分支直接补一套后端。
- 合并顺序固定为：**数据库/后端与契约 → Web/H5 → 小程序 → 联合测试**。
