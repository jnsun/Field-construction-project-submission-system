## 一、状态、证据与变更规则

### 1.1 状态枚举

| 状态 | 含义 | 可进入下一状态的条件 |
| --- | --- | --- |
| `原文待补录` | 未获得可核对的原始业务要求 | 原计划正文及责任人确认后，拆分验收条件 |
| `未实现` | 要求已明确但没有可定位实现 | 代码、迁移、策略和测试均已完成后转为“待回归验证” |
| `部分完成待回归` | 已定位部分实现，仍有缺口或未验证项 | 补齐缺口并取得自动化/人工证据 |
| `待回归验证` | 代码或资料已完成，尚未通过回归和签收 | 关联测试通过且人工验收留下证据 |
| `已验证待签收` | 自动化和人工验收均通过，待业务负责人签收 | 业务负责人签收并附证据链接 |
| `已签收` | 业务负责人完成签收 | 后续变更需新增验收编号，不回写历史 |
| `阻塞` | 缺少前置条件、原文、环境或审批 | 阻塞原因关闭并记录证据 |

### 1.2 证据规则

1. “已开发”一律不能直接写为通过，至少先标记为 `待回归验证`。
2. 每条验收记录必须有代码/数据库/接口三项定位；尚未定位时必须明确写 `未发现`，不能留空。
3. 自动化测试可为静态审计、单元、集成或 E2E；没有测试时写 `未发现`，并在异常路径注明不能签收。
4. 证据链接可指向提交、测试报告、Supabase SQL Editor 结果截图存放位置或经批准的发布记录；不记录凭据、Cookie、密码或密钥。

### 1.3 需求变更规则

1. 新增或变更业务规则必须先在本文件新增 `Txx-ACnn`（或 `CHG-YYYYMMDD-xx-ACnn`）条目，再修改代码、SQL 或配置。
2. 新条目必须写明原始要求、角色、正常路径、异常路径、数据库/RPC/RLS/Storage 影响、自动化测试和人工验收；未知项写 `未发现` 或 `原文待补录`。
3. 已签字、已发布、已归档或已产生培训档案的数据变更，必须新增迁移、回滚方案和审计证据，不覆盖历史验收记录。
4. 每次实现任务的交付说明必须引用本矩阵中的验收编号，并把状态更新为 `待回归验证` 或更高状态；未引用编号的改动不得视为已纳入需求。
5. 试点发布门仅当其下全部验收条目达到 `已验证待签收` 或 `已签收`，且线上 RLS/Storage/函数权限核验有证据时才可放行。
